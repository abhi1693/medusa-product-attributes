# Medusa Product Attributes 0.0.1

First public release of reusable typed product attributes for Medusa v2.

## Included

- Editable, versioned attribute templates in native Admin settings: create, duplicate, revise, archive and delete unused definitions.
- Multiple templates per product, explicit applicable fields, optional one-level subsections, and independent product/variant values.
- Text, bounded numeric values with declared units, Yes/No, single choice and multiple choices.
- Immutable owned revisions, atomic current pointers, public Product/Variant links, optimistic concurrency and confirmed stale-write recovery.
- Partial draft authoring, publication validation, eligible Store reads and protected internal history.
- Optional application authorization, separate template/value capabilities and explicit metadata-export permission.
- Seed-once editable definitions preserving staff changes, archives and deleted keys.
- Typed client exports for server and browser integrations.

## Install

```sh
npm install @abhi1693/medusa-product-attributes@0.0.1
```

Register the plugin once and run the application’s normal `medusa db:migrate` before startup. The validated host uses Medusa 2.22.2, UI 4.2.9 and Vite 7.3.7. Node 22.22 or newer is required; CI uses Node 24.21 and npm 11.19.0. Review the repository’s dependency-compatibility notes for root overrides on this baseline.

## Development preview migrations

Normal module migrations retain owned histories and convert earlier singular assignments into ordered groups. The final schema removes the obsolete template `source` column; existing definitions remain editable. Runtime `templates` configuration and the old synchronization CLI are not release APIs. Replace preview synchronization wrappers with an explicit `seedDefinitions` bootstrap, or manage templates in Admin. Database migrations do not rewrite merchant catalog facts or native commerce records.

The plugin owns revisions rather than native metadata. Any prior application-specific data backfill is separate from these schema migrations. Test a backup and upgrade in a nonproduction copy before changing an existing application.

## Integration limits

- Search/filter/comparison flags describe fields; storefront rendering, filtering, facets and indexing are separate integrations.
- Decimal numbers and bounds are supported; integer-only constraints and unit conversion are not provided.
- Schema updates require explicit product adoption. Incompatible values or missing required fields on published products are rejected.
- Native hooks use supported public workflow extensions and compensation, without a shared transaction or global serialization across native modules. Existing hook owners must explicitly compose the exported validation handlers.
- Store responses require a complete current revision, publication and channel eligibility; there is no older-revision fallback.

See the README for configuration, authorization grants, API contracts and workflow ownership.
